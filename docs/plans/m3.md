# M3 Workers: vertical slices

Breakdown of the M3 milestone from [PLAN.md](../PLAN.md), 2026-09-04. Vocabulary is
[CONTEXT.md](../../CONTEXT.md); M1's slices are in [m1.md](./m1.md) and M2's in [m2.md](./m2.md). M3 is done
when the M2 scenario — a Claude Code loop picks up an assigned Issue, writes a plan Document, hits the Plan
Gate, and resumes after a Human approves — runs on a free Cloudflare account.

Ten slices, in dependency order. Each is one PR on `main` that leaves the Docker image deployable and the
Worker build green, and carries its own tests. Nothing in a slice is needed by an earlier one.

M3 is the first milestone whose subject is not a feature. Almost nothing here is new behaviour: it is the
same core, on a second runtime, plus the three things M2 left behind. That makes the slices unusually easy to
get wrong in one particular way — a change that makes Workers work and quietly costs Node something — so
every slice below states what must stay true on Node, and the Node tests M2 already wrote are the regression
suite for all ten.

## Decisions taken for M3

- **Node stays the primary target.** Workers is a second deployment, not a migration. Every slice leaves
  `apps/server`, the Docker image and their tests behaving identically. Where the two runtimes need different
  numbers — poll intervals, sweep limits, stream lifetimes — the difference is an argument the entry passes,
  never a branch inside `packages/core`. There is no `if (workers)` in the core, and a slice that wants one
  has found a missing parameter.
- **One app per isolate, not one per request.** `apps/web/src/worker.ts` calls `createApp` per request today.
  That rebuilds the oRPC handlers, the OpenAPI spec and the MCP server every time; with slice 5 it would also
  construct a Better Auth instance per request, whose constructor touches the database, and `principal.ts`
  caches a verified JWKS in a `WeakMap` keyed by the `Auth` object, so a per-request instance re-fetches the
  key set on every token it verifies. M3 caches the app in module scope keyed by the `env` object — one entry
  per isolate, no globals to reset between tests — and `buildContext` stays the only per-request work.
- **drizzle-kit stays the only generator; wrangler is the only applier on D1** (ADR-0008). The migrations
  wrangler applies are a committed projection of drizzle's output, regenerated by a script and diffed in CI
  exactly like `openapi.json` and `mcp-tools.json` (ADR-0009). The two runtimes keep two journals —
  `__drizzle_migrations` on Node, wrangler's own table on D1 — over one schema. That is safe because it is
  never one database: a D1 database is only ever migrated by wrangler and a SQLite file only ever by the Node
  migrator.
- **A binding the free plan does not have is an optional binding.** Queues are a paid Workers feature and
  M3's definition of done is a free account, so the queue binding is optional in the `Env` type and absent
  from the committed config: present, a delivery gets a nudge; absent, the next Cron pass finds the same row a
  beat later. `jobs.ts` already committed to this in M2 — "the durable row is the record and the queue is
  only a hint about when to look at it" — and M3 is where that sentence earns its keep. The same rule applies
  to anything else the slices find behind a paywall.
- **The `Cron` port does not survive contact with a Cron Trigger, so the pass moves into the core.**
  `Cron.every(seconds, run)` describes a scheduler that keeps running and hands back a stop function;
  Cloudflare hands a one-shot `scheduled(controller, env, ctx)` and owns the schedule itself. Rather than
  write a Workers `Cron` that lies about who owns the timer, the body of `startRunner`'s sweep moves to
  `packages/core/src/work.ts` as `runDueWork(...)`, which both entries call: Node keeps its timer and its
  drain loop, the Worker calls it once per trigger with tighter limits. `Cron` stays what it always was, the
  Node port.
- **The Workers metadata transport narrows the DNS-rebinding gap; the Node one closes it.** PLAN.md says M3 is
  where it closes, and on Node that is true: `node:dns` resolves, the addresses are checked, and the
  connection uses the address that was checked. On workerd there is no primitive that pins an address to a
  connection while preserving SNI, so the Workers transport gets a DoH pre-resolution on top of today's shape
  check and the residual race is documented rather than claimed away. Slice 8 spikes the alternatives first
  and reverses this if one works.
- **A stream ends before the platform ends it.** `subscribeToEvents` polls once a second, and each poll is one
  D1 query, so a per-invocation query cap turns directly into a stream's lifetime (PLAN.md's risks put that
  cap at 50). The Workers stream therefore closes itself cleanly, after a heartbeat carrying its cursor, and
  the client resumes from that cursor — which `useLiveEvents` already does after a drop, so this costs the SPA
  a few lines rather than a design.
- **Widen the MCP surface rather than narrow the sentence.** PLAN.md offers M3 the choice on "manage Labels
  and Links"; widening is right, because the sentence describes what an Agent actually needs. M2's reasoning
  that an Agent may create Labels but never update or delete them is unchanged and stands.
- **Secrets are secrets.** `wrangler.jsonc` is committed and holds no credential: `wrangler secret put` for
  deployments, `.dev.vars` locally, and `.dev.vars` added to `.gitignore`, which today's `.env.*` line does
  not match.
- **`assets.run_worker_first` is part of the routing table, not configuration.** A path `createApp` mounts
  that is missing from that list is answered by the asset handler with the SPA's `index.html` — a 200 with the
  wrong body, which no test of `createApp` can see. Slice 4 asserts the list against the app's own routes.

## Deferred out of M3

Postgres as the third adapter; Durable Objects, which would replace the SSE poll with a real bus and end this
milestone's most awkward compromise; Hyperdrive; read replication and multi-region; per-Agent rate limits at
the edge (M2 turned the API-key plugin's limiter off and said the edge owns it; the edge is now real, and this
is still not the milestone for it); deploying the Worker from CI on a tag, which needs an account the project
does not have; the reference agent runtime and its operator docs (M4); the Slack app.

## Conventions every slice follows

M1's eight-step definition of done ([m1.md](./m1.md)) and M2's five additions ([m2.md](./m2.md)) hold
unchanged. M3 adds four:

15. Anything the Worker entry does gets a test that runs on workerd. `vp run web#test:workers` boots
    `wrangler dev --local` against a migrated local D1 and drives it over HTTP; a unit test of a function the
    Worker happens to call proves the function and never the binding.
16. Both runtimes' configuration is documented in one table in `docs/OPERATIONS.md`: the env var on Node, the
    binding or secret on Workers, the default, and what breaks when it is absent. A knob that exists on only
    one target says so in that table.
17. A `wrangler.jsonc` change ships in the same PR as the `vp run web#check:workers` run that proves it: the
    dry-run deploy is that file's typecheck.
18. No `process.env` anywhere in the Worker path, and no configuration read at module scope. Bindings arrive
    on `env`, per request, and whatever is derived from them is cached keyed by that object.

Sizes are t-shirt estimates for one developer plus agents: S under a day, M two to three days, L a week.

## Dependency order

```
M2
├─ 1 The MCP surface matches the promise     no Workers dependency; parallel from day one
├─ 2 One delivery, once                      the guard M2 lost; parallel
└─ 3 The schema on D1
   └─ 4 The Worker serves deevy
      ├─ 5 Sign-in on the Worker
      │  ├─ 7 Live updates inside a Worker's budget
      │  └─ 8 A client metadata document, fetched safely
      └─ 6 Background work on a Cron Trigger
         └─ 9 Queues, for an account that has them    needs 2
            10 M3 release: the agent loop on a free account
```

Slices 1 and 2 are M2's unfinished business and depend on nothing in M3. They are first because they are
small, and because carried debt that waits for the release slice is how it becomes M4's.

## Slice 1: The MCP surface matches the promise (S)

**Goal.** "Manage Labels and Links" over MCP means what PLAN.md says it means.

**Depends on.** M2.

**Schema.** None.

**Core.** Four meta changes and one rule. `labels.create` gains `mcp: true`; it has had `agents: true` since
M2. `links.list` and `links.remove` gain `agents: true` and `mcp: true`. `links.remove` gains the rule that
makes that safe: an Agent may remove only a Link its own Run attached, which is what `issue_link.runId` (M2
slice 2) was for. An Agent that can remove any Link can erase another Agent's evidence, and the Event log
would record it as housekeeping. `labels.update` and `labels.delete` stay Human-only for M2's reason —
Labels are Workspace-scoped, so a granted Agent deleting one reaches Projects it cannot see — and that
reasoning has not changed.

**Operations.** No new ones. The snapshot goes from seventeen tools to twenty.

**UI.** None.

**Acceptance test.** Core: `mcp-tools.json` contains `labels_create`, `links_list` and `links_remove`, and
still does not contain `labels_update`, `labels_delete` or `gates_approve`; an Agent removing a Link its own
Run added succeeds, and one another Run added is `FORBIDDEN`; `labels_delete` called by name over MCP is
refused rather than merely hidden. The snapshot diff in CI is what keeps it honest. PLAN.md's v1 tool list is
edited in the same PR to name the twenty that ship.

## Slice 2: One delivery, once (S)

**Goal.** The invariant M2 meant to have: at most one outbound attempt owed per destination per Event, and
sending the same row twice sends one message.

**Depends on.** M2. Nothing in M3 — build it any day.

**Schema.** `delivery` gains unique `(target, targetId, eventSeq)`. M2 slice 5 specified unique
`(subscriptionId, eventSeq)` and lost it when slices 5 and 8 merged Slack and webhooks onto one table with a
`target` discriminator, where it became a plain index. `notification` gains unique
`(recipientMemberId, kind, eventId)` for the same reason and in the same migration: the inbox is derived from
the Event in the same tail and has the same shape of invariant, one index away. Each `CREATE UNIQUE INDEX` is
preceded by a delete of any exact duplicate keeping the earliest row, so an instance that somehow has one
still migrates instead of failing halfway.

**Core.** Both derivations in `appendEvent`'s tail insert with `onConflictDoNothing`, so the invariant is
enforced by the schema and not merely respected by the one caller. The send is made provably idempotent
rather than incidentally so: `deliverDelivery` returns without a request when the row it claimed already has
`deliveredAt`, and the claim query already skips those rows. `webhooks.redeliver` is unaffected — it updates
the row in place rather than inserting a second one, which is now the only thing it could do.

`remindAboutGates` is the one caller the key changes, and it changes because the key forces it rather than
because the slice wanted to. It re-derives the Notification its Gate already wrote, which used to add a second
identical inbox row and now cannot, so a reminder becomes that Notification coming back unread: the sweep
clears `read_at` for the Event it re-derived. That is the better reading anyway — nothing has happened in the
Workspace, and the ask is the same ask nobody has answered. The cost is that a Slack Channel owed one message
for that Event no longer gets a second one when the reminder fires, which is what one attempt per destination
per Event means.

**Why now.** Queues are at-least-once (slice 9), and today deevy has neither the schema guard nor a test that
says a duplicated message costs one POST. The guard and the idempotent send are different halves of that, and
both belong before anything can deliver a message twice.

**Acceptance test.** Core: running the derivation for one Event twice leaves one `delivery` row and one
`notification` row; delivering the same row twice POSTs once and the second call makes no request at all; two
concurrent `deliverDueWebhooks` still claim disjoint sets; `webhooks.redeliver` on a delivered row still
resets and re-sends it; a Member owed two Notifications of different kinds for one Event still gets both, so
the unique key is the right one; a Gate reminder past its silence window brings the approver's existing
Notification back unread rather than writing a second one, and leaves the Slack Channel's one `delivery` row
for that Event alone. Migration: applied to a database with existing deliveries and notifications,
it succeeds, and applied to one holding a hand-made duplicate it succeeds and leaves the earlier row.

## Slice 3: The schema on D1 (M)

**Goal.** `wrangler d1 migrations apply` builds exactly the schema `packages/db` describes, and CI proves the
two have not drifted.

**Depends on.** M2.

**Schema.** No new tables. A second projection of the same migrations.

**Work.**

- `packages/db/scripts/emit-d1-migrations.ts` writes `packages/db/migrations/NNNN_<name>.sql`, one file per
  drizzle folder in journal order, committed to the repository. Wrangler applies the files in that directory
  in order and records what it applied in its own table.
- The projection is not a copy. drizzle-kit separates statements with `--> statement-breakpoint` comments,
  which wrangler does not read; the emitter rewrites those into plain statement separation, and refuses —
  loudly, naming the file and line — any statement D1 will not take, rather than emitting a file that fails
  halfway through a production deploy. The set of refused statements is discovered by applying the existing
  twenty migrations to a local D1 in this slice, not guessed.
- `packages/db/package.json` gains `generate:d1`, and `generate` chains it, so a schema change cannot produce
  a drizzle migration without its projection. `check:migrations` grows a third check beside the `NOT NULL`
  guard: every drizzle folder has a projected file, and every projected file is what the emitter would write
  today. A stale projection fails CI exactly like a stale `openapi.json`.
- `apps/web/wrangler.jsonc` gains `migrations_dir` pointing at `packages/db/migrations`, and the placeholder
  `database_id` is left as it is: local D1 does not read it, and the release slice documents replacing it.

**What must stay true on Node.** The Node migrator keeps reading `packages/db/drizzle` and nothing about the
runtime path changes. The projection is a build artifact of the same source.

**Acceptance test.** Node: the emitter's output for the twenty existing migrations is byte-for-byte what is
committed; adding a drizzle folder with no projection fails `check:migrations`; a fixture migration containing
a statement D1 rejects fails the emitter with its file and line. Workers:
`wrangler d1 migrations apply deevy --local` against an empty local D1, then
`wrangler d1 execute --local --command "select name from sqlite_master where type='table' order by name"`
lists exactly the tables `packages/db/src/schema` defines — the expected list is derived from the schema
module, so a new table without a migration fails the test rather than needing someone to update a fixture.
Applying twice is a no-op. Both run in CI.

## Slice 4: The Worker serves deevy (M)

**Goal.** A deployed Worker serves the SPA, the API, the docs and the MCP challenge off D1: everything M1 and
M2 built that does not need a signed-in Human.

**Depends on.** 3.

**Schema.** None.

**Work.**

- `apps/web/src/worker.ts` stops calling `createApp` per request. A module-level `WeakMap<Env, App>` builds
  the app the first time an isolate sees a binding set, and every later request in that isolate reuses it.
  M0's "no auth yet" comment stays for one more slice; the shape it sits in changes now, so slice 5 is about
  authentication and not about lifecycle.
- `readWorkerEnv(env)` beside `apps/server/src/env.ts`, returning the same shape minus the file paths, so the
  two entries visibly configure one app rather than two apps that happen to agree.
- `assets.run_worker_first` gains `/mcp` and `/.well-known/*`. Both exist since M2 and neither is reachable on
  the Worker today: the asset handler answers first and returns `index.html`, so an MCP client's discovery
  request gets a 200 full of HTML.
- A test that the list covers the app. Hono exposes its registered routes, so the assertion is mechanical:
  every path `createApp` mounts that the SPA does not own must be matched by an entry in `run_worker_first`.
  This is the one thing in M3 that can break silently in production while every unit test passes.
- `.dev.vars.example` beside `.env.example`, and `.dev.vars` added to `.gitignore` — the existing `.env.*`
  line does not match it.
- `vp run web#test:workers`: a smoke script that boots `wrangler dev --local` against a migrated local D1 and
  drives it over HTTP, added to CI after `check:workers`. It is a script rather than a vitest file because
  `apps/web`'s test config is jsdom and this is neither jsdom nor node.

**Acceptance test.** Workers, against `wrangler dev --local`: `/healthz` answers; `/api/docs` renders and
`/api/spec.json` matches the committed `packages/core/openapi.json`; `/issues/DEV-1` returns the SPA's
`index.html` while `/api/issues/DEV-1` returns JSON — the pair that `run_worker_first` gets wrong silently;
an unauthenticated `/rpc` call is `UNAUTHORIZED` with a JSON body rather than a crash; an unauthenticated
POST to `/mcp` is 401 carrying the `WWW-Authenticate` challenge M2 slice 3 defined. Node: the route-coverage
test fails when a route is added to `createApp` and not to the list, and the Docker smoke is unchanged.
Manual: `wrangler deploy` to a free account and the same checks against the `workers.dev` origin.

## Slice 5: Sign-in on the Worker (L)

**Goal.** A Human signs in with GitHub on the Worker and lands in the Workspace, on D1.

**Depends on.** 4.

**Schema.** None: the auth tables came from the generator in M0, M2 slice 1 and M2 slice 7, and slice 3 gives
D1 all of them.

**Work.**

- `createAuth` in the Worker path, configured from `env`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`,
  `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `DEEVY_ADMIN_EMAIL`, `DEEVY_WORKSPACE_NAME`. Cached per isolate
  with the app, which is what makes the JWKS cache in `principal.ts` and Better Auth's own initialisation
  something an isolate pays for once instead of per request. This is the whole of PLAN.md's "token
  verification workaround for a shared Worker" that M2 did not already ship: `verifyJwsAccessToken` with an
  in-process `jwksFetch` has been in `principal.ts` since M2 slice 7, and what was left was making its cache
  key outlive a single request.
- Bootstrap on D1. `bootstrapWorkspace` and `joinWorkspace` run from Better Auth's user and session hooks,
  sequentially, with no transaction — which is exactly why they work here unchanged (ADR-0006), and worth
  saying out loud as the first real payment for that constraint.
- **The request budget**, and the reason this slice is an L. D1 caps queries per invocation (PLAN.md's risks
  say 50), and a signed-in write already costs the session and user lookup, the Member and Workspace, an
  Agent's grants, the handler's own reads and writes, and then `appendEvent`'s tail: the Event insert,
  `deriveNotifications` with its routing reads, `deriveWebhookDeliveries`, and `triggersFor`, which may append
  a further Event with a tail of its own. Nobody has counted it. This slice counts it first and fixes what the
  count names, rather than optimising by guesswork. Two candidates if it needs them: Better Auth's session
  cookie cache, which replaces two queries per request with a signed cookie, and hoisting the routing reads in
  `deriveNotifications` out of the recursion. The recursion in `appendEvent` is the interesting one — a
  trigger's Event pays a whole tail of its own — and it is a real finding either way.
- `packages/core/tests/helpers.ts` gains a counting database wrapper built on drizzle's `logger` option, so
  the budget is a test with a number in its name and not a note in a document.
- `docs/OPERATIONS.md`: the GitHub OAuth App callback URL for a `workers.dev` origin and for a custom domain,
  and why `BETTER_AUTH_URL` must equal the origin the browser actually uses — `auth.ts` pins the OAuth issuer
  and the RFC 8707 resource identifier to it, so a wrong value produces tokens bound to a host nobody visits.

**What must stay true on Node.** Nothing about `apps/server`'s wiring changes. If the budget work touches
`deriveNotifications` or `appendEvent`, M1 and M2's tests for both are the regression suite, and the statement
count on Node is asserted by the same test with the same number.

**Acceptance test.** Workers, against `wrangler dev --local` with a stubbed GitHub: the admin email's sign-in
creates the Workspace and one admin Member on D1 and appends `workspace.created` then `member.joined`; a
second sign-in adds nothing; the session cookie the Worker minted authenticates `/rpc/members.list`; a sign-in
matching an allowlisted email domain auto-joins, and one matching nothing gets a user row and no Member.
Core: creating an Issue with one mention, one Slack Channel and one webhook subscription costs no more than
the asserted number of statements, and the test says what the number is and what cap it is under. Manual:
sign in on a deployed Worker with a real GitHub OAuth App, create a Project and an Issue, reload, everything
is still there.

## Slice 6: Background work on a Cron Trigger (M)

**Goal.** The stale sweep, the schedule trigger, the Gate reminder and both delivery loops run on Cloudflare,
inside one trigger's budget.

**Depends on.** 4.

**Schema.** None.

**Work.**

- The `sweep` function inside `apps/server/src/runner.ts` moves to `packages/core/src/work.ts` as
  `runDueWork({ db, now, limits, baseUrl?, signal? })`: the same five passes in the same order, still bounded,
  still no timer, and the Workspace lookup moves with it. `startRunner` keeps the timer, the drain loop, the
  overlap guard and the SIGTERM behaviour, and calls it. The Worker's `scheduled(controller, env, ctx)` calls
  it once through `ctx.waitUntil`.
- The Worker passes tighter limits on purpose: one pass per trigger and a smaller row limit, because a
  trigger has a CPU budget and a per-invocation query cap and a Cron Trigger comes back on its own. `more:
true` has meant "come back rather than raise the limit" since M2 slice 2; on Workers the thing that comes
  back is the platform.
- `wrangler.jsonc` gains `triggers.crons` at one minute, the finest Cloudflare offers, which makes
  `DEEVY_SWEEP_INTERVAL_SECONDS` a Node-only knob. The configuration table says so.

**What must stay true on Node.** `startRunner`'s behaviour, exactly: the drain loop, no overlapping ticks, no
leaked timer, and a stop that waits for the pass in flight. This is the slice most likely to break the Node
deployment while every Workers test passes, and M2's runner tests are the guard.

**Acceptance test.** Workers: `wrangler dev --local --test-scheduled`, then a request to `/__scheduled`; a Run
whose `lastActivityAt` is 31 minutes old is `stale` afterwards with its `run.went_stale` Event, and a second
trigger changes nothing; with 60 due Runs and a limit of 20, one trigger moves 20 and three triggers move all
of them, which is the bounded-pass contract stated as a test. Core: `runDueWork` with a signal aborted between
passes stops there and reports what it did. Node: M2's `startRunner` tests pass unmodified, and the process
still exits.

## Slice 7: Live updates inside a Worker's budget (S)

**Goal.** The board updates itself on Workers too, and a stream that has to end says where it got to.

**Depends on.** 5.

**Schema.** None.

**Work.** `subscribeToEvents` gains `maxDurationMs` beside its existing `pollMs`. It ends by returning after a
final heartbeat carrying the cursor, so a subscriber resumes exactly rather than reconnecting blind. The
Worker entry passes a duration inside whatever this slice measures the platform to allow, and a slower
`pollMs`: at one D1 query per poll, the per-invocation query cap is the real ceiling on a stream's life, and a
two-second poll doubles it at the cost of a second of latency on a board nobody is watching that closely.
`useLiveEvents` reconnects immediately after a clean end and keeps its two-second wait for a failure — a
stream that ended on purpose is not an error and should not cost the user two seconds of staleness.

**What must stay true on Node.** The Node entry passes no `maxDurationMs` and its streams stay open as they
do today; the default is unbounded, so the parameter is invisible to `apps/server`.

**Acceptance test.** Core: a stream with `maxDurationMs` returns after it, and its last message is a heartbeat
carrying the seq of the last Event it yielded; a stream's queries are bounded by `maxDurationMs / pollMs`,
asserted with the counting database from slice 5; an Event appended after the stream ended is delivered to the
next stream started from that cursor, so nothing falls in the seam. SPA: a stream that ends cleanly is
resubscribed with `after` set to that cursor and without the failure delay. Workers: two browsers on
`wrangler dev --local` both see an Issue move within one poll, and a stream that has run past its limit
reconnects without the user noticing.

## Slice 8: A client metadata document, fetched safely (M)

**Goal.** Close the DNS-rebinding gap where it can be closed, narrow it where it cannot, and say plainly which
is which.

**Depends on.** 5.

**Schema.** None.

**Spike, first day of the slice.** Whether workerd can pin the address it validated for an arbitrary
third-party host: `cf.resolveOverride`, which is documented for zones on the account rather than for the
internet at large, and `connect()` from `cloudflare:sockets`, which dials an address and gives no way to set
SNI separately from it, so TLS validates against the address. If either turns out to work, take it and the
decision below reverses. Plan for neither.

**Work.**

- `packages/adapters/src/node/cimd.ts`: the strict transport for Node. Resolve with `node:dns`, check every
  returned address against the same public-routability rules `packages/core/src/cimd.ts` already applies to
  literals, then connect to an address that passed with the hostname preserved for SNI and certificate
  validation. `apps/server` passes it as `AuthEnv.fetchClientMetadataResource` — the seam M2 left for exactly
  this, and the reason no core file has to change to get the stricter behaviour. Whether the implementation is
  ours or `@better-auth/cimd/node` re-exported is a slice-time decision: the plugin ships one, and if it does
  this it is a wiring change and a test.
- `packages/core/src/cimd.ts` keeps the shape check, which is all Workers can rely on, and gains a DoH
  pre-resolution ahead of it: ask a resolver over HTTPS for A and AAAA, refuse if any answer is not publicly
  routable, then fetch by name. That refuses every name that resolves privately at the moment of the check.
  What it still cannot refuse is a name that answers publicly to the resolver and privately to the connection
  a millisecond later, and the module's own comment already says so.
- `docs/OPERATIONS.md` states the residual risk per target, replacing the current paragraph that describes
  only the shape check. PLAN.md's M3 sentence — that this is where the gap closes — is corrected in slice 10
  to what shipped.

**Acceptance test.** Core: the Workers transport refuses `http://`, a URL carrying credentials, a redirect, a
body over 128 KB, and a document whose name resolves to `10.0.0.1` through a stubbed DoH resolver; a
publicly-resolving name is fetched. Node: the adapter transport refuses a name that resolves to a private
address, and — the case a shape check can never catch — a stubbed resolver that answers public and then
private is refused, because the connection uses the address that was checked. Wiring: a test asserts which
transport each entry passes, so a future refactor cannot quietly give Node the weaker one.

## Slice 9: Queues, for an account that has them (M)

**Goal.** On an account with Queues, a delivery goes out when it is written rather than when the next trigger
comes round. On an account without, nothing changes at all.

**Depends on.** 6, and 2 for the guard.

**Schema.** None.

**Work.**

- `packages/adapters/src/workers/queue.ts`: `createQueueJobQueue(binding)` satisfying `JobQueue`. Its
  `enqueue` never throws and never rejects, because the port says so and because it is called in the tail of a
  request that has already written the durable row.
- `worker.ts` gains a `queue(batch, env, ctx)` consumer that calls the single-message delivery function per
  message, acks on success and on permanent failure, and retries otherwise. At-least-once is why slice 2 came
  first: a message delivered twice must cost one POST, and now there is a test that says so.
- `AppOptions` gains an optional `jobs?: JobQueue` defaulting to `discardingJobQueue()`, threaded to the
  derivation in `appendEvent`'s tail. Nothing on Node passes one; the Worker passes one only when the binding
  exists.
- The binding is optional in the `Env` type and absent from the committed `wrangler.jsonc`, so
  `wrangler deploy` on a free account cannot fail on a queue it is not allowed to create. If the slice finds
  Queues are in fact available on the free plan, nothing about the shape changes — an optional binding that is
  always present costs one branch.

**What must stay true on Node.** `apps/server` passes no queue and its delivery path is the sweep, unchanged.

**Acceptance test.** Core: with a stub queue, deriving a delivery enqueues exactly one job carrying the row's
id and no payload; a queue whose `enqueue` rejects does not fail the request that wrote the row, and the sweep
still delivers it. Workers: on `wrangler dev --local` with a local queue, a webhook is delivered without
waiting for a trigger; the same message delivered twice POSTs once; a consumer failure retries and the eighth
attempt appends `webhook.exhausted` exactly as the sweep would. Free-plan shape: `wrangler deploy --dry-run`
with no queue block succeeds, and the same webhook is delivered by the Cron path alone.

## Slice 10: M3 release, the agent loop on a free account (M)

**Goal.** The milestone's own definition of done, on Cloudflare, from a tag.

**Depends on.** 1 through 9.

**Work.** `docs/OPERATIONS.md` gains a Cloudflare section: create the D1 database and put its id in

codebase is the claim ADR-0006 makes and this is the only test that checks it.
