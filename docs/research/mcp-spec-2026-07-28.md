# Research: MCP spec status as of 2026-09-03

## Revisions
- Current stable: **2026-07-28** (released 2026-07-28; RC locked 2026-05-21). Previous: 2025-11-25. Draft: empty.
- Deprecated with 12-month window (earliest removal 2027-07-28+): Roots, Sampling, Logging, Dynamic Client
  Registration, HTTP+SSE transport.

## "Stateless" = protocol core change (SEP-2575 + SEP-2567 + SEP-2322 MRTR), not a transport option
- No initialize handshake; every request carries _meta protocolVersion + clientCapabilities. Mandatory server/discover.
- No protocol sessions, no Mcp-Session-Id. Cross-call state = server-minted opaque handles passed as tool args.
- Streamable HTTP: single endpoint, POST only (GET/DELETE -> 405). Required headers MCP-Protocol-Version, Mcp-Method,
  Mcp-Name (+ optional Mcp-Param-*). Response = JSON or request-scoped SSE.
- Server-to-client requests (elicitation, sampling) only as `input_required` results (MRTR): client retries the
  original request with inputResponses + echoed opaque requestState (MUST be integrity-protected, bound to principal/TTL).
- Notifications: progress/log on the request's own stream; list_changed etc. only via opt-in long-lived
  `subscriptions/listen` POST stream. Resumability removed (re-issue request). Durable long work -> tasks extension.
- list/read results MUST carry ttlMs + cacheScope.
- Dual-era servers may serve legacy (2025-11-25 and earlier, with sessions) and modern; legacy client vs modern-only
  server -> 400.

## Elicitation
- Modes form and url (per-request capability). URL mode required for secrets/credentials/payment; accept = consent
  to open; server checks requestState/own store on retry for completion. Server MUST verify the same user completes it.

## Authorization
- OAuth 2.1, PKCE S256 mandatory. MCP servers MUST implement RFC 9728 Protected Resource Metadata; AS MUST expose
  RFC 8414 or OIDC discovery. Client registration: pre-registered -> CIMD (client_id = HTTPS URL; AS advertises
  client_id_metadata_document_supported) -> DCR (deprecated) -> prompt. RFC 8707 resource param mandatory; audience
  validation; no token passthrough.
- Non-interactive clients: OAuth Client Credentials extension (draft; no clients support it yet).
  Claude connectors support oauth_dcr, oauth_cimd, and static_headers (beta) for admin-entered API keys; Codex
  supports bearer_token_env_var. Enterprise-Managed Authorization extension stable 2026-06-18 (Okta XAA; Claude, VS Code).

## TypeScript SDK v2.0.0 (2026-07-27)
- Packages: @modelcontextprotocol/server, /client, /core, /node, /express, /fastify, /hono, /server-legacy, /codemod.
  Node >= 20. Legacy @modelcontextprotocol/sdk 1.30 does NOT speak 2026-07-28.
- Stateless server: `createMcpHandler(factory, { responseMode, legacy: 'stateless'|'reject', bus })` builds a fresh
  McpServer per request; returns { fetch, close, notify, bus }. Context { era, authInfo, requestInfo }.
  Hono: `createMcpHonoApp()` + `app.all('/mcp', c => handler.fetch(c.req.raw, { parsedBody }))`.
  Web-standard runtimes (Workers/Bun/Deno): `export default handler`. Auth is pass-through: verify bearer yourself,
  pass authInfo.
- MRTR API: `inputRequired({ inputRequests: { x: inputRequired.elicit(...) | elicitUrl(...) }, requestState })`,
  `createRequestStateCodec({ key, ttlSeconds })`. Legacy shim turns input_required into real elicitation for 2025 clients.
- Multi-node: nothing shared except `subscriptions/listen` bus (pass a pub/sub ServerEventBus).

## Clients
- Claude Code: 2026-07-28 default since v2.1.232 (HTTP + connectors), form/URL elicitation, CIMD, subscriptions/listen.
- Claude.ai/Desktop: "rolling out soon" (2026-07-28 post). Codex: opt-in since 0.147.0 (2026-08-07).
  VS Code: no doc yet. Cursor: not aligned (DCR missing application_type). GitHub MCP server: since 2026-07-23.

## Implications for deevy
- Use TS SDK v2 @modelcontextprotocol/server + /hono, `legacy: 'stateless'` to serve 2025-era clients too.
  Stateless per-request handler runs identically on Node and Cloudflare Workers.
- deevy must be an OAuth 2.1 AS with RFC 9728 PRM + CIMD support for Human MCP clients (Claude Code, Codex);
  DCR only as legacy. Agents: bearer API keys issued by deevy (deevy is the AS, so keys are "tokens it issued").
- Gate approvals via URL elicitation is a natural fit: agent hits a Gate -> input_required with a deevy URL -> Human
  approves in the UI -> agent retries. Skip `subscriptions/listen` in v1 (needs a shared bus on Workers).
- Long-running agent work: agents are external (ADR-0003), so deevy doesn't need the tasks extension for its own tools.
